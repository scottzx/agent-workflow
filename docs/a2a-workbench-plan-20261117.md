# A2A 工作台开发计划

- 日期：2026-11-17（Asia/Shanghai）。
- 状态：计划。下文阶段均为待实现，不代表当前部署已具备。
- 源码基线：`develop` 上的交接提交 `f8d392c7`。交接、约定、共享产物空间登记和只读边投影已进账本；工作台页面还不能按一件事操作这些边。
- 产品判断：要做的是 A2A 工作台。自媒体发布是第一块基线应用，用来逼出工作台缺的能力，不把平台做成剪辑器或渠道后台。
- 不跟进 LoopForge 作为底座。它成熟的是软件交付：编码 Agent、仓库、PR、画布式 SOP。可以借用待确认收件箱、运行留痕，以及把会跑命令的步骤放进沙箱。不引入流程设计器，不把 GitHub 需求当成交付合同。

## 1. 工作台与应用的边界

工作台回答四件事：这一件事情是什么，谁在做，人批的是哪一版，批准之后可以交给谁。

应用回答内容怎么做：搜新闻、选题标准、镜头、素材、配乐、渠道登录、群发、什么叫数据好。公众号补库已经把应用侧的库存规则写清：可发布只算审核通过且未发布的一篇；待审和在做的不算库存；发出去的不能因为重读又回到库存。平台不重写这套规则，只提供「外部回执必须对上某一版字节」。

| 留在工作台 | 留在自媒体应用 |
| --- | --- |
| 一件事、任务、轮次、交接、约定 | 策划、检索、选题标准和镜头单 |
| 版本、digest、预览 | 剪辑、找素材、配乐、合成 |
| 待确认、谁有权点这一下 | 各平台登录、上传、群发 |
| 外部回执和外部事实的入口 | 指标含义、经营复盘结论 |
| 执行目标、角色、产物空间登记 | 素材库和成片工程文件的业务格式 |

画布只投影账本。已发生的边是实线，提议是虚线，还没发生的约定只写在当前节点上。不提供节点面板，不把未发生的路径画出来。

## 2. 已有能力，不重做

- Job、Attempt、绑 `resultRevision` 和 `resultDigest` 的业务验收。
- 任务单：同一张任务上的检查、质检、打回和修改，不是角色之间的交接。
- 人工审核与过程请求；工作台已有全部任务、待我确认、进行中、异常，以及智能体的试跑和上线。
- 交接方法：`handoff_propose`、`handoff_decide`、`handoff_offer`、`handoff_space`、`handoff_get`。提议和接受都不派单。下一张任务要另调 `execution_submit` 并带 `handoffId`。多条约定同时成立时不自动挑选。
- 三种目录：任务目录、角色公开目录、按 `caseId` 登记且必须事先存在的共享产物空间。
- 执行目标、A2A 网关、设备容量、可选的 Activepieces 触发。定时看库存、拉平台数据继续放在触发器里，不放进通用调度器。

执行中的 ACP 会话还没有交接工具。网关侧已能接收执行方用 `jobId`、`attemptId`、`sessionId` 发起的提议（`invokeHandoff` 的执行方分支），缺的只是会话里的工具入口。基线先让人在工作台点选；角色自己提议交接晚于这一步。

### 2.1 已有能力中的缺口（2026-11-17 对照 `f8d392c7` 源码复核）

以下是现有实现与本计划约束不一致之处，P0 必须先补，不能当作已具备：

- 版本绑定不完整。`execution_submit` 带 `handoffId` 开单时，`resultRevision` 取 `input.resultRevision ?? handoff.artifactRevision`，调用方另传的版本不被比对；也不核对来源任务当前结果是否仍是被接受的那份 digest。任务目录按 `jobs/<jobId>/` 固定，来源任务再跑一轮后，下游可能读到新字节，账本却绑着旧 digest。
- 决定可被冒称。A2A 的 `handoff_decide` 接受调用方自填的 `decidedBy: {kind:'person'}`，智能体也能这样写，与第 5 节「不把智能体声称用户已同意当成可核验的决定」冲突。网关已有 `PAGE_ONLY_ROUTES`、`pageRelaySecret` 和 `reviewerId` 可复用。
- 一件事没有实体。`caseId` 只是任务上的字符串；约定、产物空间、交接都按 `(originSessionId, caseId)` 分区。页面上的人不对应某个 `originSessionId`，也没有记录目标的位置。
- 约定默认自动接受。`handoff_offer` 的 `requireHuman` 默认 `false`：验收通过即记成已接受的交接。

## 3. 阶段

### P0：一件事能被看见、被点、被批

没有这一阶段，自媒体只是一堆任务，工作台还不能当基线应用的入口。

0. 先定 case 数据模型，再做页面。需要写清并实现：
   - case 记录写进账本，字段至少有 `caseId`、目标、创建时间、创建者、所属 `originSessionId`。
   - 由显式方法创建（例如 `case_open`，页面与 A2A 共用）；`handoff_space`、`handoff_offer`、带 `caseId` 的提交只能引用已存在的 case，不隐式创建。已有只带 `caseId` 字符串的历史任务按兼容方式投影，不重写旧记录。
   - 作用域先保持按 `originSessionId` 分区；页面按网关可见的全部主会话列出 case。是否允许跨主会话共享同一件事，留到有真实需求时再定，不在 P0 做。
1. 一件事。工作台第一屏是 case，不是 Job 列表。一件事有目标、共享产物空间、其下的任务、交接和待确认。`caseId` 不再只出现在交接记录上。选题是第一件这样的事。
2. 只读投影。页面画出已发生的交接和未打开的提议，不发明终点。当前节点显示允许的下一跳（`legalNext`），以及条件是否已经成立（`achieved`）。已登记的约定写在当前节点上，标明是否要求人确认；`requireHuman` 为 `false` 的约定要明示「验收通过即自动成立交接」。
3. 页面动作。接受或拒绝提议只能在页面上做：
   - 新增页面路由并加入 `PAGE_ONLY_ROUTES`，经 `pageRelaySecret` 中转，决定记录为 `{kind:'person'}` 并带上配置的 `reviewerId`。
   - A2A 通道的 `handoff_decide` 若声明 `kind:'person'` 则拒绝；教练只能以 `kind:'coach'` 并写明会话的方式记录，页面上与人的决定分开显示。
   - P0 只有单一审核人；按关口指定不同的人留到 P2。
   开下一张任务是另一次明确动作，带上 `handoffId`，网关核对目标、目的、父任务以及版本（见第 6 条）。
4. 一个收件箱。审核、过程请求、交接提议进同一列「待我确认」。批的是这一版，答的是这一问，接受的是这一次交接。
5. 产物按版本打开。一件事里按 revision 和 digest 列出稿、图、音频、成片，并按类型预览。预览不是剪辑。人必须能看见自己在批什么。
6. 版本绑定补齐：
   - 带 `handoffId` 开单时，调用方传的 `resultRevision` 若不等于 `handoff.artifactRevision` 则拒绝。
   - 接受交接时把被接受的产物冻结为按 digest 寻址的只读快照（或复制进该 case 的共享产物空间），下游任务读取快照而不是来源任务目录；读取时再次校验 digest，不一致即拒绝。
   - 来源任务之后的新一轮不影响已接受交接所指的字节；要交新版本必须重新提议。

完成标准：用一件模拟的选题，不靠命令行，完成「建一件事、看见产物、批准这一版、接受交接、打开下一张任务」。以下各项须有自动化测试：

- 旧批准不能放行新版本：来源任务再跑一轮后，已接受交接仍只交出原 digest 的字节；另传版本号开单被拒。
- A2A 调用以 `kind:'person'` 决定交接被拒；页面决定记录带 `reviewerId`。
- 同一个 `handoffId` 重复开单返回同一张子任务。
- 刷新或重启后，case、边和决定仍在。

### P1：闭环能接到外面

1. 对外回执。发布不是把任务状态改成完成。回执记录 digest、渠道、对方 id、链接和时间。公众号先用这一条，以后的渠道仍用它。重读不能把已发布的算回库存。登录和群发留在应用。开工前须定下：
   - 挂载点：回执挂在 case 上，并引用产物 digest（以及产生它的 job/attempt），不挂在任务状态上。
   - 写入入口：新增专用方法（例如 `receipt_record`），只接受页面或应用持有的凭据写入；智能体不能凭自述登记。
   - 防重键：`渠道 + 对方 id`；同键不同 digest 视为冲突而非覆盖。
   - 迁移：公众号补库现有「已发布」登记一次性导入为回执，导入后应用只读回执，不再维护自己的已发布状态；导入范围和对不上 digest 的旧记录要单列，不推测补齐。
2. 约定在页面上可见、可登记。网关判断与自动接受已在 `continueByConvention`、`proposeHandoff` 中实现（只有一条、且不要求人确认，才记成已接受；多条不挑选；不派单），这一条不重做，只补页面登记与展示，例如「稿子通过后可交：剪辑」。若 P0 第 2 条已覆盖展示，本条只剩页面登记。
3. 外部事实。播放、完读、涨粉作为事实进入这件事：时间、指标、数值、来源。过线只产生交接提议，例如建议改标题或重切，不自动再发一条。平台不解释指标好坏。须写明：阈值作为该 case 上的一条约定条件存进账本，由网关比较并以网关身份发起提议；Activepieces 只负责把事实交进来，不判断过线。

完成标准：一条已发布回执对得上成片 digest；同一渠道同一对方 id 不能登记第二个 digest；一条低于目标的事实只生成提议，不产生新的发布任务。

### P2：交给别人操作，以及会跑命令的步骤

1. 每道关口有被指定的人。交接接受、发布放行和结果验收都校验这个人。先不做完整账号体系。
2. 沙箱是执行目标的配置档，不是工作台形态。会跑 ffmpeg、下载素材的目标才使用。默认不把宿主凭据和 Docker socket 交进去。等人不占着执行环境。
3. 执行中的角色可以提议交接，但仍不能自己派下一单。网关侧执行方提议已就绪，本条只补 ACP 会话里的工具入口，不重写提议逻辑。这一步晚于页面点选，不阻塞基线。

完成标准：未被指定的人不能接受交接或登记发布回执。一个会跑命令的目标在配置档指定的环境里执行，失败不影响同一件事里其他人的待确认。

## 4. 基线应用怎么用来验收工作台

自媒体第一块基线只要求工作台把下面这条链跑通，不要求平台内置剪辑或渠道客户端。

```text
选题批准 → 逐字稿批准 → 剪辑或拍摄任务打开 → 成片批准 → 发布回执 → 数据事实 → 策略提议
```

应用自己提供检索、文稿、剪辑和发布动作。工作台负责版本、交接、收件箱和回执。拍摄可以是人完成后再把成片放进产物空间，不要求工作台控制摄像机。

公众号补库继续作为已有应用，不改成 SOP。它的库存、审核和发布登记应能引用 P1 的回执，而不是另造第二套「已发布」状态。

## 5. 明确不做

- 不把策划到发布画成可编辑流程图。
- 不把编码 Agent 名单、GitHub PR 或 MySQL 团队站当作工作台前置。
- 不在平台里做报表、素材库、配乐库或渠道适配。
- 不因两条约定同时成立而自动挑选下一跳。
- 不因数据过线而自动发布。
- 不把智能体声称「用户已同意」当成可核验的决定。

## 6. 建议顺序

P0 先于任何新的自媒体角色。P1 与第一条真实发布渠道一起做，渠道只消费回执接口。P2 在有第二个人操作，或有步骤必须离开宿主目录时再做。

Activepieces 只保留定时检查和外部数据拉取。它把事实交给工作台，不代替交接和验收。
