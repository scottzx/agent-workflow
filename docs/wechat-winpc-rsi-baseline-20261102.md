# 微信自动回复基线：训练过程与总结（2026-11-02）

## 结论

收消息、判断、排队、发送和确认入库的整条链路，已在真实微信上跑通，基本达到预期。这还是人工陪测，还不能无人值守，也还没接入 `rsi run`。

- **场景：** WinPC 上的微信测试账号，由运行在 Mac 上的 Grok CLI 值守。
- **测试会话：** 单聊 `wxid_PEER`，群 `2404图灵测试`。
- **硬限额：** 每个会话每分钟 1 条，全部会话每分钟 5 条。

## 过程中定下的规则

- 测试账号不设发送白名单。
- 粘贴的 @ 只是普通文字，所以群回复写成「名称，内容」，队列拒绝 `@名称`。
- 第一版不用成员列表 @，也不用引用回复。
- 群里按人分别排队和回复。
- 每条回复最多 80 字。一条说不完可以多发，但每条都计入硬限额。
- 群消息只有真正 @这个账号（按 ID 判断），或引用它的消息，才调用模型。
- 调用模型时，带上这个群上次处理之后新增的所有消息。
- 引用等同于 @，但由模型判断要不要回。

## 回答速度

从检测到对方消息到回复入库，不含等待发送名额：

| 批次 | 样本 | 范围 | 中位数 |
|---|---|---|---|
| 第 2 批（改队列前） | 6 条 | 6.5–17.6 秒 | 9.4 秒 |
| 第 3、5 批（按轮处理） | 7 条 | 6.6–22.0 秒 | 10.9 秒 |

普通回复的速度和第 2 批差不多。样本很少，这点差异不能说明变快或变慢。最慢的两条（约 20 和 22 秒）都是模型耗时长，原因还没查清。

确实改善的地方：

- **交接：** Grok 空闲时 0.02–0.22 秒，第 2 批最慢要 3–5 秒。
- **群里闲聊：** 没 @ 的消息不调用模型，不会耽误下一条。
- **连发：** 连发 3 条只回 1 条，约 63 秒全部答完。如果逐条回，第 3 条至少还要多等 2 分钟。

## 工具层优化

| 环节 | 优化 | 实测 |
|---|---|---|
| 收信 | 增量解密 WAL，0.5 秒轮询，写入独立的库 | 第 3、5 批 0.53–1.68 秒 |
| 发送 | 不用截图和 OCR，直接搜索会话、粘贴、回车 | 约 1.6 秒，其中 1.5 秒是固定等待 |
| 发送确认 | 在库里查到自己的消息才算发出，查不到就暂停，不重试 | 回车到入库 0.06–0.51 秒，没有重复发送 |
| 限额 | 由程序保证，不依赖模型 | 第二条回复排队 61 秒后发出；全局 5 条只有单元测试 |
| 队列 | 每个会话里每个人一个未回复队列，有发送名额才调用模型 | 不积压草稿，中断后消息不丢 |
| @ 判断 | 从文字匹配名字改成读 `atuserlist` 里的 ID | 手打“@晓风宝”不再触发 |
| 引用 | 引用我们的消息等同于 @ | 已验证会触发 |
| 群上下文 | @ 时带上新增的群消息 | 模型能结合前文判断 |
| Grok 入口 | 只有 `next`、`reply`、`skip` 三条命令 | 中断后接原会话恢复成功，它还记得前文 |

## 判断结果

- **第 5 批：** 判断都符合规则。
- **指令注入：** 第 3 批和第 5 批各有一次索要系统提示词，都被拒绝。
- **越界发送：** 第 2、3、5 批的报告都显示，测试会话以外没有多发消息。

## 过程中的错误和修正

- **账号名写错：** 提示词一直把账号叫“晓风宝”，但联系人昵称是曾晓峰。第 2 批漏回 2 条，第 3 批漏回 1 条。第 2 批的报告曾写“漏回复 0”，后来更正。
- **手打的 @：** “@晓风宝”只是普通文字，`atuserlist` 为空，不是真的 @。曾误判为“两个名字都算”，后来更正。
- **文字拼接合并：** 先做了排队回复的拼接，读起来不连贯，也可能重复。已改为有发送名额时让模型一次处理全部未回复消息。
- **回复顺序：** 第 2 批恢复时，重新入队的命令写错，单聊两条回复的顺序反了。
- **工具范围：** 曾以为 Grok 只能用 `./wx`，实际网页搜索不受 `--allow` 约束，可以直接运行。

## 还没验证

- 同一个群里两个账号同时 @。
- 按 ID 判断规则下的 @所有人。目前不触发，要不要回还没决定。
- 引用我们的消息后，模型选择跳过。
- 全局每分钟 5 条的限额压测。

## 接入 RSI 前要解决

1. **ACP 工具限制：** fork 会话初步报告，DSH 和 RSI 走 ACP 启动 Grok，`--allow` 和 `--disable-web-search` 都没有入口，实测被限制的动作也能运行。这部分还在 fork 会话里继续测试，结论以那边为准。
2. **进程守护：** 一次越权就会中断值守，这次是手动恢复的。
3. **远程桌面断开：** 断开后发不出消息，也没有告警。`tscon` 方案会让机器长期不锁屏，还没决定。
4. **进程重启：** 入库和队列程序退出后不会自己恢复。
5. **上下文上限：** 接活跃群之前需要加。

## 建议阈值（还没锁定）

| 指标 | 建议 |
|---|---|
| 不含排队的回复时差 | P95 ≤ 25 秒，单条 ≤ 40 秒 |
| 含排队的总时差 | 单条 ≤ 100 秒，不含积压和中断 |
| 误回复、漏回复、重复回复 | 都是 0 |
| 收信时差 | 单条 ≤ 3 秒，超过算环境问题 |
| 超出限额的发送 | 0 |

样本还不够，P95 现在基本等于最大值，这组只适合作为初版。
