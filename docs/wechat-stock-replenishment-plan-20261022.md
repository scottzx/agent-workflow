# 公众号内容补库业务方案

- 日期：2026-10-22（Asia/Shanghai）。
- 2026-10-23补充：由AP承载监测与条件触发，agent-workflow 继续提供执行与任务事实；技术接点见[实施方案](wechat-stock-replenishment-implementation-20261023.md)。
- 2026-10-23实施补充：已补齐真实业务接点，参数为低于10篇启动、补足15篇，每30分钟检查。公众号暂留空使用候补内容池；正式启用与派单证据见实施记录，原规则演练草稿保持禁用。

第一版只负责一件事：当指定公众号的可发布库存低于下限时，按既定篇目顺序调用“公众号系列编辑”制作文章发布包；生产量补足后等待，发布消耗库存后再次检查。把已经跑通的单篇制作能力，接成一个可以持续工作的补库闭环。

## 1 目标与职责

当前素材为《企业数智化转型研究报告》上中下三册。上游事先确定每篇文章对应的原文范围、系列期号和生产顺序；补库器领取篇目，不自行重新策划拆分。首版沿用导论试跑的原文保留要求，只补充标题、摘要、封面、页脚、正文HTML和系列导航。

进入可领取清单的篇目，应已具备原文、明确制作要求，并满足进入制作的授权条件。用户已明确授权三册已定稿原文直接封装，记录冻结原文与授权引用，不虚构选题和大纲通过；普通素材仍遵守现有前置审核。成品人工审核始终保留。

| 对象 | 职责 | 存续方式 |
| --- | --- | --- |
| 公众号补库器 | 检查库存、领取篇目、派单、跟踪结果、保存进度 | 规则与状态持续保留；没有工作时等待 |
| 公众号系列编辑 | 按合同制作一篇完整发布包并交付校验结果 | 复用已登记的固定角色 `wechat-series-editor` |
| 单篇制作任务 | 处理一个确定篇目及其输入版本 | 一次Job有明确交付与终点；修订保留任务历史 |
| 人工审核 | 判断当前版本是否可进入发布库存，处理修改意见与例外 | 沿用现有审核流程 |

本版范围到内容补库为止。公众号登录上传、群发、效果取数、经营复盘、调整账号定位和自动开发新选题，留在各自业务环节。人工发布并登记，也可以触发下一轮补库。

## 2 库存和生产占位

可发布库存只统计目标范围内的真实文章：完整发布包已经验收、当前版本审核通过，而且尚未发布。当前公众号待补，先按独立候补内容池统计，绑定账号后保留原篇目和动作身份。每个篇目只算一篇，多个稿件版本不能重复计数；已发布篇目不因下架、重启或重新读取记录而自动回到库存。

发布包沿用现有编辑角色的交付约定：发布标题、不超过100字的摘要、16比9封面、正文预览和全内联HTML、复用页脚与系列导航，以及原文保留和制作校验记录。文件生成成功、任务执行成功、通知已读，均不能单独代替成品审核通过。

补库时同时读取以下三个数量，按篇目去重，并保证同一篇只处于其中一类：

| 数量 | 含义 | 是否计入可发布库存 | 是否占生产位置 |
| --- | --- | --- | --- |
| R | 当前有效版本审核通过、完整且未发布 | 是 | 是 |
| P | 制作验收合格，等待人工审核 | 否 | 是 |
| A | 已领取且正在制作，或派单结果尚待确认 | 否 | 是 |

有效占位数为 `E = R + P + A`。占位用于决定还要生产多少，不能显示成已经拥有的可发布库存。例如“可发布9篇、待审核6篇”，不能写成“可发布15篇”。

原文更新、改稿或重新审核必须关联原篇目和版本。首版在新版替换当前稿件后，旧版不再重复计入库存；新版通过前保留为待审或待处理。篇目处于修改、失败或未知状态时，不得换一个任务编号把它当作全新文章重复领取。

## 3 启动下限与补足目标

| 规则 | 本轮参数与约定 |
| --- | --- |
| 启动下限 L | 10篇；`R < 10` 时启动补库，恰好10篇且无活动批次时不启动 |
| 补足目标 T | 15篇；本轮持续朝15篇可发布库存补充 |
| 同时执行数量 | 最多一个制作或返工任务 |
| 篇目选择 | 按已排定顺序领取下一篇未处理文章 |
| 检查入口 | 启用、人工检查、制作完成、审核变化、发布登记后重新检查；部署时可配置周期检查兜底 |

启动下限与补足目标分开，避免库存每减少一篇就频繁启停。若业务要求始终在每次消耗后立即补回，可另行调整参数；本方案采用“跌破下限后补足一轮”。

补库批次一旦启动，就保存该轮目标，正常情况下实际库存 `R >= T` 才结束。中途从9篇增加到10篇，仍继续本轮；若有效占位 `E >= T`，先停止新派单并等待审核。人工审核可以与逐篇制作并行，待审稿件继续占位，因此不会因人工尚未审核而无限生产。若原文篇目耗尽，已有任务和待审稿件收尾后，以“素材耗尽、库存未补足”结束；没有新增篇目时不重复启动空批次。

## 4 一轮补库怎样推进

1. 先检查是否启用及暂停状态。未启用或已暂停时，不创建补库批次、不领取篇目；已有任务结果仍可核对、登记和收尾。允许推进时，读取目标公众号的稿件、审核、发布和在途任务事实；读取失败或状态不确定时保留原进度，等待核对，不把未知库存当作零。
2. 没有进行中的补库批次时，若 `R >= L`，结束本次检查；若 `R < L`，创建并保存本轮补库目标。
3. 已启动的批次先判断 `R >= T`，满足则结束本轮；否则检查正在制作或待确认的任务，有则等待该任务结果。
4. 没有在途任务时，若 `E >= T`，等待人工审核；若 `E < T`，从固定清单领取下一篇，保存篇目占位和派单关联，再调用现有编辑角色。
5. 制作交付通过校验后，将该篇从A转为P，保留占位并再次判断是否还需制作。人工审核通过后从P转为R，再次检查。
6. 发布记录确认已发布后，从R中扣除该篇；若已经跌破下限，或当前补库批次尚未结束，则按上述规则继续。

```text
检查真实库存
    ↓ 低于下限，或已有补库批次
检查在途任务和待审占位
    ↓ 仍有生产缺口
领取下一篇 → 调用系列编辑 → 制作验收 → 人工审核 → 入库
    ↑                                                   ↓
    └────────────── 重新检查 ────────────────────────────┘

占位已足：等待审核；实际库存补足：结束本轮等待；发布消耗：重新检查。
```

典型场景：

| 当前情况 | 应有动作 |
| --- | --- |
| R为9、P为0、A为0 | 启动补库，逐篇制作，直到有15个有效位置；等待审核通过 |
| R为9、P为6、A为0 | 已占15个位置，等待审核，不继续生产 |
| R为9、P为5、A为1 | 等待当前制作任务，不能重复领取下一篇 |
| R为10、P为0、A为0，尚无补库批次 | 未跌破下限，不启动 |
| R为14、P为0、A为0，已有补库批次 | 本轮尚未达到15篇，继续补一篇 |
| R为15、P为0、A为0 | 结束本轮；后续降到10篇仍等待，降到9篇再启动 |

## 5 审核和异常处理

| 情况 | 处理约定 |
| --- | --- |
| 等待人工审核 | 保留待审占位；占位已足时等待，不自动批准 |
| 人工要求修改 | 转为待修改，暂停该补库批次并通知；首版不自动无限返工，显式修订关联原任务与原篇目、保留修订历史，是否复用原Job按现有合同规则处理 |
| 任务失败或交付不合格 | 保存失败任务与原因，暂停批次；处理后显式恢复，不自动新建任务掩盖失败 |
| 派单受理未知、写回状态未知 | 保留占位和原请求关联，先核对原任务或写回结果；不盲目重派 |
| 程序重启或重复事件 | 先读取已保存批次、占位与任务关联；同一篇只推进一次 |
| 清单还有篇目但输入或审核未准备好 | 保存待准备原因并等待，不把暂时不能领取当作原文耗尽 |
| 清单全部处理或明确跳过 | 标记素材耗尽并通知，已有在途任务与待审稿件照常收尾；库存仍不足时以“素材耗尽、库存未补足”结束，不自动扩写新素材或重复启动空批次 |
| 人工暂停 | 保存当前进度并停止新派单；已有任务继续可见，是否取消单独处理 |

制作失败和人工待修改必须有明确待处理原因。首版由人决定修改、跳过或恢复；跳过需要留下篇目记录，恢复前重新读取库存。规则检查和人工等待期间，无需保持模型持续运行。

## 6 AP 与 agent-workflow 的载体和边界

第一版由Activepieces（AP）承载“观察变化、条件判断、执行预定动作”的感应式工作流；补库器在本方案中指这组AP流程。agent-workflow 复用现有统一目标、任务账本和通知机制，不增加公众号库存监测循环。条件按确定性规则判断，需要制作时才调用模型，不建立经营目标规划或策略优化系统。

| 载体 | 保存内容 |
| --- | --- |
| 公众号业务配置与篇目清单 | 目标账号、库存下限、补足目标、固定生产顺序、原文版本及编辑目标引用 |
| 老板IP现有飞书工作台 | 文章成品版本、人工审核、发布记录；作为库存事实来源 |
| AP流程与运行记录 | 监测触发、条件分支、动作调用和异步结果处理；每次运行只推进有限动作 |
| 工作台业务适配的持久状态 | 规则启停、当前批次与目标、篇目占位、稳定动作键、关联Job、结果写回状态和待处理原因；提供原子领取与幂等登记 |
| agent-workflow 任务账本与自动化关联 | 真实Job/Attempt、执行状态、结果版本、AP运行关联和持久通知；不保存另一份补库调度状态 |
| 单篇产物目录 | 正文快照、标题摘要、封面、HTML、校验记录和交付清单 |

业务运行状态扩展工作台已有持久存储，并遵循项目`.1agents/`目录约定，独立于某一次AP运行或聊天。原主会话是通知接收位置，不能作为唯一进度载体。业务表格和任务账本已有的事实通过引用关联，不另建一套互相覆盖的文章数据库。

现有飞书字段能够表达稿件版本、审核状态和发布记录，补库还需增加篇目与任务的稳定关联及待审占位规则。当前仍需实施库存读取、判断、派单、验收写回和恢复衔接；不能把现有编辑角色完成过一次制作等同于补库已经上线。

AP负责持续检查和规则分支；“什么算一篇可发布公众号文章”、报告顺序和飞书字段映射留在公众号业务适配中。agent-workflow 保持执行受理、状态核对与通知职责；现有AP计划派发尚需补齐固定角色及业务动作键桥接，不能直接视为补库已接通。主会话继续遵循提交保存回执后结束本轮、真实通知到达后处理的约定。

## 7 第一版验收

| 验收点 | 通过条件 |
| --- | --- |
| 正常补库 | 从9篇库存出发，按固定顺序逐篇制作，获得15个有效位置后停止新派单；全部审核通过后显示15篇可发布并结束批次 |
| 审核未完成 | 9篇可发布加6篇待审时不继续生产，待审稿件不显示成可发布 |
| 保持本轮目标 | 启动后库存升到10篇仍继续补至15；没有补库批次时10篇不启动 |
| 发布触发 | 从15篇降到10篇保持等待，降到9篇后自动启动下一轮 |
| 防止重复 | 重复检查、重复通知和程序重启都不重复领取篇目、重复派单或重复登记成品 |
| 异常可处理 | 审核退回、任务失败及状态未知时停止新增生产，保留原关联并说明待处理原因 |
| 素材收尾 | 原报告篇目处理完后明确提示，完成已有任务收尾；未达到目标时仍以素材耗尽结束，后续检查不反复创建空批次 |
| 暂停生效 | 人工或异常暂停后，发布事件与周期检查均不能触发新派单；恢复后重新读取库存再推进 |

第一版衡量的是补库是否准确、连续、可恢复。公众号经营效果与策略优化，作为后续独立范围评估。
