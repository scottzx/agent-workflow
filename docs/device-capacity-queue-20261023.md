# 设备容量与 FIFO 等待队列

自动召唤在准备启动时读取当前可用内存，保留系统和用户余量；不足时等待，不反复新建实例。设备级账本由同一操作系统用户的多个项目、服务实例共享。

## 启动条件

每次准入在同一把跨进程锁内完成：清理可证明失效的记录、读取实时内存、检查并发限额、预占新实例预算，然后允许启动。

```text
可用于本次启动的内存 = 当前可用内存 - 保留余量 - 其他启动中的预占预算
允许启动 = 可用于本次启动的内存 >= 单实例估计内存，并且未达到适用的并发上限
```

- 默认单实例预算为 1 GiB，可按实际 Agent 占用配置。它是保守估计，不是内存隔离或 OS 强制限制。
- 默认保留物理内存的 10%，最少 512 MiB、最多 4 GiB。交互来源也不能越过这个内存保护条件。
- 预估上限 `soft` 约为 CPU 数的一半与每 3 GiB 一个实例的较小值；至少 1。自动召唤在这个上限内运行。
- 极限上限 `hard` 参考 CPU 数与每 2 GiB 一个实例，至少比 `soft` 大 1，为宿主明确标记的用户交互保留空间。此值是并发保护阈值，不宣称硬件实测极限。
- 所有判断以启动瞬间的可用内存为准。CPU、总内存推算的数量只是另一个上界，不能覆盖实时内存不足。

macOS 通过 `vm_stat` 读取空闲、inactive 与 speculative 页，估计当前可回收空间；不把压缩内存或 swap 当作新增容量，也不叠加可能重合的 purgeable 页。解析失败回退到系统空闲内存。其他平台取系统空闲内存与 Node 可用内存的较小值，兼顾进程/容器约束。读数和硬件估算均不是可承诺的最大可分配内存。

启动期预占窗口为 30 秒，弥补“已批准启动，但内存尚未实际分配”的时间差。未登记 PID 的进程始终保留启动预算；已登记进程与任务超过窗口后由实时读数反映用量，但并发名额仍保留。提交执行前的 `recheck()` 重新采样并刷新窗口。

## 排队与执行

资源不足的自动任务在持久 FIFO 中保持等待。A2A 对外使用标准 `TASK_STATE_SUBMITTED`，状态文字说明 `Pending`；不会发送模型 prompt。调用方能立即得到 taskId、查询或取消，等待不会变成任务失败。

队列默认每 750 毫秒重新检查。只有队首可以申请，满足内存和并发条件后出队；同时容纳多个任务时依次启动，不要求前一个完成后才启动后一个。取消移除对应队项。任务完成、失败或取消后释放任务名额，进程必须等退出事件才释放进程名额。

取消信号贯穿容量等待与后端会话准备；后端必须先撤销、清理自己持有的初始化，再完成取消。DSH 原生 `create` 是宿主自有的非中止操作，若取消时已经进行，等待其返回后停止后续恢复和 prompt，可能保留一份空白原生会话记录，不擅自删除宿主历史。它本身不启动 ACP 子进程或提交模型 prompt。

ACP `session/new` 在客户端尚未收到新 ID 时也能取消：服务端用内部 ID 撤销对应进程队项，并等待初始化清理。取消 `load/resume` 的重新附着不会停止原先已运行的用户会话，也不会关闭后来成功接管它的连接。

会话准备完成后，以及 DSH 会话自身的串行等待结束、准备提交 prompt 前，再次检查内存。不足则释放任务名额并重新等待，复用已准备好的会话，不重新创建会话或重复提交 prompt。DSH 宿主原生 inbox 内已有的人工请求仍由其自己的调度器执行，本层检查边界是提交 prompt。

FIFO 的顺序是进入设备队列的持久序号；同一上下文的会话互斥、角色技能准备在进入该队列之前完成。进程与任务分别排 FIFO，避免父任务挡住其子进程。各进程的队列共用同一目录、序号和原子锁，不按某个业务的 3 并发配置分裂。

## 覆盖范围与保留空间

- A2A 自动任务在 `backend.prepare()` 前申请任务名额，生命周期结束释放。
- ACP 服务的所有进程启动都经过 runtime 生命周期钩子，包括兼容性探测、启动诊断与 Grok 预热，按实际 launchId/PID 申请和释放进程名额；资源不足时也进入进程 FIFO。
- 任务并发与进程并发分别统计。启动内存预算只由进程占用：任务本身不分配内存，它的 ACP 子进程会作为进程单独申请，所以任务名额不再预占单实例估计（2026-10-31 起；此前两份会叠加）。任务准入仍要过实时内存检查。
- Grok 预热进程被任务接管时，若这个任务之前因名额不足在进程 FIFO 里留了队项，接管时一并撤销。否则这条队项停在队首，后面所有进程启动都会一直等（2026-10-31 并发测试里出现过）。
- 用户在原生 Codex、DSH 等应用中的直接操作不被本队列拦截；它们使用的内存会自然反映到下一次实时检查。通过 ACP 服务新建的 Agent 仍属于受控启动。
- 嵌入宿主可通过可信 `source: interactive` 使用软硬上限之间的余量。远端任务 metadata 无法选择此优先级或覆盖容量配置。
- 本层不会为腾空间强杀运行任务，亦不强制回收空闲的持久会话。持久进程达到上限时需要关闭不再需要的会话，后续队项才继续。

## 配置与恢复

默认设备账本在 `~/.1agents/state/acp-capacity/`，独立于项目会话目录与 `ACP_STATE_DIR`。它属于本机宿主资源协调数据，不提交 Git。项目任务与角色数据继续遵循项目 `.1agents/` 约定。

| 宿主环境变量 | 含义 |
| --- | --- |
| `ACP_CAPACITY_DIRECTORY` | 同一设备各受控服务共享的账本目录 |
| `ACP_CAPACITY_SOFT_LIMIT` | 自动并发上限，正整数 |
| `ACP_CAPACITY_HARD_LIMIT` | 最终并发上限，必须大于 soft |
| `ACP_CAPACITY_MEMORY_RESERVE_MB` | 保留内存，MiB，可为 0 |
| `ACP_CAPACITY_INSTANCE_MEMORY_MB` | 单实例启动估计，MiB，必须大于 0 |

A2A 嵌入配置也可使用可信的 `capacity` 对象（`directory / softLimit / hardLimit / memoryReserveBytes / estimatedInstanceBytes`）。相同设备目录的活跃实例必须使用相同策略；配置冲突拒绝准入，避免不同服务以较高阈值绕过保护。清空在途租约后可更新策略。

账本保存 owner PID 与已启动的 child PID；活进程不按超时抹掉。父服务退出但子进程仍活着时继续占位；父服务退出且还没有登记 child PID 时不能证明是否已启动，保守保留，需宿主人工核对后清理。不会凭 PID 记录杀进程。

队列文件跨进程保存顺序，但不用于恢复原模型执行。排队 owner 已退出时移除其队项；A2A 重启沿用现有“标记中断、不自动重跑”的恢复语义。坏账本、锁失败或不明存活状态不能被当作空容量。

本轮仅修改源码并验证；不代表共享宿主已经部署或正在运行的旧进程已纳入账本。
